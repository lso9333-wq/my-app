# MyDoctor — AI 훈련 및 추론 데이터 확보 작업계획

작성일: 2026-09-11
대상: "분석 정확도 문제 해결 + 영상/결과 축적 → AI 훈련 → 우리만의 DB 구축" 비전 검토 및 실행계획

---

## 0. 요약 (먼저 결론부터)

사용자가 말한 "정확도 문제"와 "AI를 훈련시켜서 결과를 낸다"는 두 가지는 사실 **서로 다른 층위의 문제**입니다. 이걸 먼저 구분하지 않으면 계획이 꼬입니다.

1. **지금 겪고 있는 정확도 문제(기기 간 결과 차이)**는 대부분 "새 AI 모델을 학습시켜서" 풀리는 문제가 아닙니다 — PC와 폰이 같은 영상을 서로 다른 GPU/디코더로 처리해서 미세하게 다른 픽셀·랜드마크 값을 만들어내는, **하드웨어 비결정성** 문제에 훨씬 가깝습니다(One Euro Filter, 고정 그리드 샘플링으로 이미 완화 작업을 했고, 완전히 없앨 수는 없다고 CLAUDE.md에도 명시돼 있음).
2. 반면 "영상을 모아서 AI를 훈련시켜 정확도를 올린다"는 것은 **완전히 다른 종류의 정확도** — 즉 "BlazePose가 뽑아낸 관절 좌표를 우리 도메인(보행/스트레칭/XMSK)에 맞는 임상적으로 의미 있는 숫자로 바꾸는 계산식/모델 자체의 정확도"를 말합니다. 이건 실제로 데이터를 모아서 개선할 수 있는 영역이 맞습니다.

그래서 이 계획은 (1) 기기 간 편차 문제는 계속 별도로 다루고, (2) "데이터를 모아서 계산 로직/보정 모델을 개선한다"는 쪽에 집중해서 짰습니다.

또 하나, 계획을 짜기 전에 반드시 짚어야 할 충돌이 있습니다: **지금 앱은 "영상은 서버로 전송되지 않고 브라우저 안에서만 분석됩니다"를 홈 화면에 명시된 약속으로 걸어두고 있습니다.** "동영상을 축적해서 AI를 훈련시킨다"는 이 약속과 정면으로 부딪힙니다. 아래 1장에서 이 충돌을 어떻게 풀지부터 정리합니다.

## 1. 핵심 전제: 개인정보 약속과 데이터 축적의 충돌을 어떻게 풀 것인가

### 1-1. 현재 약속
- 홈 화면에 "영상은 서버로 전송되지 않고 브라우저 안에서만 분석됩니다"라고 명시.
- 실제 구조도 그렇게 되어 있음: 포즈 추정(BlazePose)은 클라이언트 브라우저에서 실행되고, 서버(`server/data/rom.db`, SQLite)에는 **영상에서 뽑아낸 수치 결과(JSON)** 만 저장됨(`stretch_sessions`, `gait_diagnostics`, `xmsk_sessions`, `xmsk_evaluations`).

### 1-2. 왜 이 약속을 깨면 안 되는가
- 신체 움직임 영상은 재식별 가능성이 있는 민감한 개인 데이터입니다. 특히 재활/보행 분석 앱이라는 맥락상 "건강 관련 영상"으로 취급될 소지가 큽니다.
- 이미 사용자에게 "영상은 안 보낸다"고 밝힌 상태에서 조용히 서버 업로드를 추가하면 신뢰가 깨지고, 잠재적으로 법적(개인정보보호법/의료기기법 관련 소지) 리스크도 생깁니다.
- 1인 개발 체제에서 원본 영상을 안전하게 저장·암호화·접근통제·삭제요청 처리까지 하는 건 운영 부담이 매우 큽니다.

### 1-3. 권장 원칙 — "원본 영상이 아니라 파생 데이터를 모은다" + "명시적 옵트인"
결론부터: **원본 영상 자체는 기본적으로 서버에 보내지 않는 구조를 유지**하고, 대신 다음 두 가지로 "학습 가능한 데이터"를 확보합니다.

1. **키포인트 시계열(landmark time series)** — BlazePose가 브라우저에서 이미 계산한 관절 좌표(x, y, z, confidence)의 프레임별 시계열. 영상 원본보다 용량이 훨씬 작고(수십~수백 KB vs 수십 MB), 얼굴이 찍히지 않으며(포즈 랜드마크만), 이미 클라이언트에서 계산이 끝난 결과라 서버 부하도 없습니다. 이것만으로도 "AI 재학습"에 필요한 대부분의 데이터가 됩니다 — 나중에 3장에서 설명할 "경량 보정 모델"은 사실 원본 영상이 아니라 정확히 이 키포인트 시계열을 입력으로 씁니다.
2. **트레이너(전문가) 검증값 — Ground Truth** — 이미 XMSK에 있는 `RomXmskManualInput`(트레이너가 손목저항 등 영상으로 잴 수 없는 값을 직접 입력하는) 패턴을 넓혀서, "이 영상에서 AI가 추정한 값 vs 담당 트레이너가 직접 관찰/측정해서 입력한 실제값"을 짝지어 모으는 것 — 이게 진짜 학습 신호입니다.

**원본 영상 저장이 정말 필요한 경우**(예: 나중에 포즈 모델 자체를 재학습하고 싶을 때)에는 반드시 다음을 지켜야 합니다:
- 기본값은 항상 "off". 화면 문구를 "영상은 브라우저에서만 분석됩니다"에서 "기본적으로 브라우저에서만 분석되며, 동의하신 경우에 한해 AI 개선 목적으로 저장됩니다"로 명확히 바꾸고, 별도의 명시적 체크박스 동의(사후 철회 가능)를 받아야 함.
- 동의한 사용자의 영상만, 얼굴이 프레임에 안 걸리게 크롭/블러 처리 후, 별도 격리된 스토리지(아래 5장)에 암호화 저장.
- "내 데이터 삭제 요청" 기능을 처음부터 같이 만들어야 함(나중에 추가하면 훨씬 힘듦).

**이번 계획의 1차 버전(1차 완성)에서는 원본 영상 저장 기능 자체를 만들지 않는 것을 권장**합니다. 키포인트 시계열 + 트레이너 검증값만으로도 "정확도 개선"이라는 실질적 목표는 대부분 달성되고, 리스크와 개발 부담이 훨씬 낮습니다. 원본 영상 축적은 2차 업그레이드 이후, 정말 필요성이 확인되면 그때 옵트인 구조로 추가하는 쪽을 권장합니다.

## 2. 무엇을, 왜 모으는가 — 데이터 설계

### 2-1. 지금 이미 갖고 있는 것 (활용 가능한 기존 자산)
- `gait_diagnostics.gait_metrics_json` — 이번 세션에서 추가한, 보행 진단 시점의 전체 `GaitMetrics` 스냅샷(걸음 간격, 좌우 비교, 케이던스 등). 이미 "결과 축적"의 첫 조각이 되어 있습니다.
- `RomXmskEstimateResult.evidence: 'approximate' | 'experimental'` — 추정치마다 신뢰도 등급이 이미 태깅되어 있음. 이건 "이 추정값이 얼마나 믿을만한가"를 이미 구조적으로 표현하고 있다는 뜻이고, 나중에 "실측값과 얼마나 차이 났는지"를 이 등급별로 집계하면 바로 모델 성능 리포트가 됩니다.
- `RomXmskManualInput` / `XMSK_MANUAL_ITEMS` — 트레이너가 영상으로 못 재는 값을 직접 입력하는 기존 패턴. Ground Truth 수집의 뼈대로 그대로 재사용 가능.
- `debugStats`(프레임 채택률, 키포인트별 평균 신뢰도, `sampledTimesChecksum`) — 이미 진단 기록에 같이 저장되고 있다면, 이걸 "이 세션의 데이터 품질 점수"로 활용해 나쁜 품질의 데이터가 학습 세트에 섞이는 걸 걸러낼 수 있습니다.

### 2-2. 새로 추가해야 할 것
1. **키포인트 시계열 저장 옵션** (기존 `gait_metrics_json`처럼 계산된 요약 수치가 아니라, 프레임별 원본에 가까운 관절 좌표 배열). 매 세션 전체를 다 저장할 필요는 없고, 우선은 "진단/평가가 저장되는 시점"에만 함께 저장.
2. **"AI 학습용 데이터로 이 세션을 사용해도 될까요?" 동의 플래그** — 트레이너/사용자 단위로 한 번 물어보고 저장(세션마다 반복해서 묻지 않도록 계정/기기 단위 설정으로).
3. **Ground Truth 입력 확장** — 지금은 XMSK에만 있는 "트레이너 수동 입력" 개념을, 보행(gait)·스트레칭(rom)에도 "AI 추정값 옆에 트레이너가 실제 관찰한 값을 적어 넣는 칸"으로 넓힘. 예: 보행 분석에서 AI가 추정한 좌우 보폭 비대칭을, 담당 트레이너가 육안 관찰 기준으로 "정상/경도/중등도" 중 하나로 직접 태깅.
4. **모델/버전 태그** — 나중에 포즈 모델 버전, 계산 로직 버전이 바뀔 텐데, 저장되는 모든 결과에 "어떤 버전으로 계산됐는지"를 태깅해둬야 나중에 "버전 A vs 버전 B" 비교(회귀 테스트)가 가능해집니다. 이게 없으면 몇 달 뒤에 쌓인 데이터가 서로 다른 로직으로 계산된 것들이 섞여서 못 쓰게 될 위험이 큽니다.

### 2-3. 데이터가 실제로 얼마나 필요한가 (현실적 기대치)
- 통계적으로 의미 있는 보정을 하려면 최소 수십~수백 건의 "AI 추정 vs 트레이너 실측" 짝(paired sample)이 필요합니다. 하루 이용자가 아직 적은 초기 단계에서는 **수집 자체가 병목**이 될 가능성이 높습니다 — 그래서 이 계획의 우선순위는 "많이 모으는 인프라"보다 "정확하게 짝지어 모으는 인프라"에 둡니다(질이 양보다 훨씬 중요한 단계).
- 딥러닝 모델을 처음부터 다시 학습시킬 만큼의 데이터(수만 건 이상)는 1인 개발 체제에서 현실적 목표가 아닙니다. 아래 3장에서 이를 반영한 현실적 대안을 제시합니다.

## 3. 모델 개선 전략 비교 — 무엇을 "훈련"할 것인가

"AI를 훈련시킨다"고 뭉뚱그려 말했지만, 실제로 가능한 선택지는 아래 세 가지이고, 비용/난이도/효과가 전혀 다릅니다.

### 옵션 A. 포즈 추정 모델(BlazePose) 자체를 재학습
- 내용: 구글이 만든 BlazePose 신경망 가중치 자체를 우리 데이터로 fine-tuning.
- 필요 조건: 수천~수만 장의 정밀 라벨링된 프레임(정확한 관절 좌표 라벨), GPU 학습 인프라, 모델 학습 전문 지식.
- 평가: **1인 개발·무GPU인프라 환경에서는 비현실적**입니다. 데이터 규모도, 인프라도, ROI도 맞지 않습니다. 권장하지 않음.

### 옵션 B. 경량 보정(calibration) 모델 — ⭐ 권장
- 내용: BlazePose가 뽑아준 관절 좌표(원본 모델은 그대로 사용)를 입력으로 받아서, "이 좌표들로부터 계산한 1차 추정치를, 트레이너 실측값에 더 가깝게 보정하는" 작은 회귀 모델(예: 랜덤포레스트, 그래디언트부스팅, 또는 몇 개 층짜리 소형 신경망)을 별도로 학습.
- 예시: 지금은 "좌우 보폭 차이 = 원시 좌표에서 계산한 값 그대로"인데, 트레이너 실측 데이터가 쌓이면 "카메라 각도, 신뢰도 점수, 걸음 수 등을 입력받아 원시 계산값을 보정하는" 작은 모델을 만들 수 있음.
- 필요 데이터: 옵션 A보다 훨씬 적음 — 수십~수백 건의 짝지어진 데이터로도 시작 가능(2-3장에서 설계한 바로 그 데이터).
- 학습/배포: scikit-learn 등으로 로컬에서 학습 → 가중치를 JSON/작은 파일로 export → 서버(Node/Express) 또는 클라이언트(TensorFlow.js)에서 추론. GPU 불필요, 학습에 몇 분~몇 시간이면 충분.
- 평가: **1인 개발 체제에 가장 현실적이고 ROI가 높은 선택지.** 이번 계획의 핵심 축으로 삼음.

### 옵션 C. 휴리스틱/필터 계속 개선 (현재 진행 중인 방식의 연장)
- 내용: One Euro Filter 파라미터 튜닝, 고정 그리드 샘플링 개선처럼, "학습"이 아니라 사람이 직접 로직/공식을 다듬는 방식.
- 평가: 비용이 가장 낮고 지금도 하고 있는 방식. 다만 사람이 원인을 명확히 알 수 있는 문제(샘플링 타이밍, 필터 튜닝)에는 강하지만, "왜 이 각도가 트레이너 판단과 다른가" 같은 복잡한 패턴은 사람이 규칙으로 다 짜내기 어려움 — 이 부분을 옵션 B가 보완.

### 결론
**단기(1차 완성): 옵션 C를 계속하면서 옵션 B의 데이터 파이프라인(수집 구조)을 먼저 깐다. 데이터가 통계적으로 의미 있는 양(우선 목표: 항목별 50건 이상)이 모이면 그때 옵션 B의 보정 모델을 실제로 학습시켜 넣는다.** 옵션 A는 이 앱의 규모에서는 계획에서 제외.

## 4. Ground Truth(정답) 확보 전략 — 어떻게 "진짜 맞는 값"을 얻는가

AI를 "훈련"시키려면 정답이 있어야 하는데, 지금 시스템은 정답 없이 추정치만 냅니다. 정답을 얻는 현실적인 방법 세 가지:

1. **담당 트레이너 실측 입력 (1순위, 이미 XMSK에 패턴 있음)** — 앱을 쓰는 트레이너/전문가가 AI 추정 결과를 보면서, 본인이 직접 관찰/측정한 값을 같은 화면에서 입력. 가장 신뢰도 높은 정답 소스. 이번 계획에서 UI적으로 가장 우선 확장할 부분(2-2-3 참고).
2. **반복 재현성(test-retest) 자체 검증** — 정답값이 없어도, "같은 사람이 같은 조건에서 두 번 찍었을 때 결과가 얼마나 일관되는가"는 정답 없이도 측정 가능한 품질 지표. 트레이너 라벨이 부족한 초기에는 이걸로 "이 항목은 신뢰도가 낮다"를 먼저 찾아낼 수 있음.
3. **외부 공개 데이터셋 보강 (보조 수단)** — 보행 분석 분야에는 공개 가이트 데이터셋(예: 연구용 3D 모션캡처 기반 gait 데이터셋)이 일부 존재. 우리 앱과 촬영 조건(단일 스마트폰 카메라, 실내/외 다양성)이 달라 직접 이식은 어렵지만, "우리 도메인에서 어떤 오차 패턴이 알려진 정상 범위를 벗어나는가"를 검증하는 참고 자료로는 유용. (주의: 라이선스 확인 필수, 우선순위는 낮음)

**실행 우선순위: 1번(트레이너 실측 입력 UI 확장)을 가장 먼저, 가장 공들여서 만든다.** 이게 없으면 아무리 데이터를 모아도 "무엇이 정답인지" 모르는 상태라 학습 자체가 불가능합니다.

## 5. 인프라 / DB 로드맵 — "제대로 된 DB"로 가는 길

### 5-1. 지금 구조의 한계
- 단일 GCP VM 위 SQLite 파일(`server/data/rom.db`) — 트래픽/데이터가 적을 때는 충분하지만, (a) 동시 쓰기 성능이 약하고 (b) 키포인트 시계열처럼 부피가 큰 데이터를 넣기 시작하면 파일이 급격히 커지고 (c) 백업/복구, 분석 쿼리(예: "전체 사용자의 좌우 비대칭 분포")가 불편해짐.

### 5-2. 단계적 업그레이드 경로 (한 번에 다 바꾸지 않음)
1. **1단계 (지금~1차 완성)**: SQLite 유지. 대신 키포인트 시계열처럼 큰 JSON은 DB 안에 그대로 넣지 말고, 파일로 저장(VM 로컬 디스크의 별도 디렉토리, 파일명은 세션 ID)하고 DB에는 파일 경로만 저장 — SQLite 비대화를 막는 가장 저비용 조치.
2. **2단계 (데이터량이 실제로 늘어나기 시작하면)**: 관계형 데이터(사용자, 세션 메타데이터, 트레이너 입력값)는 **Postgres**로 이전(관리형 서비스인 Cloud SQL for PostgreSQL 사용 시 백업/장애 대응 부담이 크게 줄어듦). 부피가 큰 키포인트 시계열/원본 영상(옵트인 시)은 **오브젝트 스토리지(GCS)** 로 분리 — "정형 데이터는 DB, 대용량 파일은 오브젝트 스토리지"라는 표준적인 분리 원칙.
3. **3단계 (모델 학습을 실제로 정기 운영하게 되면)**: 학습용 데이터 추출을 위한 간단한 배치 스크립트/파이프라인(예: 주 1회 Postgres+GCS에서 학습셋을 뽑아 로컬 or 저비용 클라우드 인스턴스에서 옵션 B 모델을 재학습하고 결과 가중치 파일만 다시 서버에 배포) 구성. 이 단계에서도 상시 GPU 서버 같은 건 필요 없음 — 옵션 B 모델은 CPU로도 충분히 학습됩니다.

**지금 당장 할 일은 5-2의 1단계뿐입니다.** 2·3단계는 "정확도 문제/데이터 파이프라인이 자리잡고, 실제로 데이터가 쌓이기 시작한 뒤"에 맞춰 진행하면 됩니다 — 미리 Postgres로 옮기는 건 지금 단계에서는 과잉 엔지니어링입니다.

## 6. 단계별 로드맵 (사용자가 말한 "1차 완성 → 2차 업그레이드" 프레이밍에 맞춤)

### 1차 완성 목표: "정확도 문제 대응 + 데이터 축적 인프라 구축" (원본 영상 저장/실제 재학습 없이)

| 순번 | 작업 | 내용 |
|---|---|---|
| 1 | 트레이너 실측 입력 UI 확장 | XMSK에만 있는 수동 입력 패턴을 보행·스트레칭 결과 화면에도 추가 (AI 추정값 옆에 "실측값" 입력 칸) |
| 2 | 키포인트 시계열 저장(선택적) | 진단/평가 저장 시 프레임별 관절 좌표를 별도 파일로 같이 저장, DB엔 경로만 기록 |
| 3 | AI 학습 활용 동의 플래그 | 계정/기기 단위 옵트인 설정 + 홈 화면 개인정보 문구 갱신 |
| 4 | 결과-버전 태깅 | 저장되는 모든 추정 결과에 포즈 모델/계산 로직 버전 기록 |
| 5 | 데이터 품질 대시보드(내부용) | 트레이너 실측 vs AI 추정 오차를 항목별로 집계해 보여주는 간단한 관리자 화면/스크립트 — "지금 몇 건 모였고 오차가 얼마나 되는지" 스스로 확인 가능해야 다음 단계 착수 시점을 판단할 수 있음 |
| 6 | 큰 JSON 파일 분리(SQLite 비대화 방지) | 5-2 1단계 |

### 2차 업그레이드 목표: "실제 보정 모델 도입 + 제대로 된 DB로 이전"

- 항목별 실측-추정 짝 데이터가 목표치(우선 항목당 50~100건)에 도달하면, 옵션 B(경량 보정 모델) 첫 버전을 실제로 학습·배포.
- 데이터량이 SQLite 한계에 부딪히기 시작하면 Postgres+GCS로 이전(5-2 2·3단계).
- 그 이후에도 "원본 영상 저장"이 정말 필요하다고 판단되면, 1장에서 정리한 옵트인·비식별화·삭제권 요건을 갖춘 뒤에만 추가.

## 8. 진행 상황 업데이트 (2026-09-15) — 발가락 시뮬레이션 보정 데이터 파이프라인 착수

사용자가 "지금처럼 MyDoctor를 계속 고도화하는 게 가장 현실적이고, 나중에 실측값 데이터가 충분히 쌓이면 그때 특정 계산 로직 하나(예: 발가락 마디별 시뮬레이션 계수)를 작은 모델로 파인튜닝하는 정도로 옵션 B를 부분적으로 시도해볼 수 있는 흐름이 자연스럽겠다"는 방향을 확인해줬다. 이 절은 그 확인에 대한 첫 실행 결과를 기록한다.

### 8-1. 왜 "발가락 마디별 시뮬레이션"을 첫 대상으로 골랐나
3장(모델 개선 전략)의 옵션 B는 "AI 추정 vs 트레이너 실측 짝지어진 데이터"가 있어야 시작할 수 있다. 이미 있는 계산 로직 중 이 조건에 가장 가까운 것이 발가락 마디별 시뮬레이션(`TOE_SEGMENT_SIM_PARAMS`, `src/features/handfoot/lib/footToeEstimate.ts`)이었다 — AI가 20개 항목 전부에 "시뮬레이션 초기값"을 먼저 채워주고 트레이너가 그 위에서 확인/수정하는 흐름이 이미 있었기 때문이다(2026-09-13 업그레이드, CLAUDE.md "발가락 마디별 시뮬레이션" 절 참고). 다만 지금까지는 트레이너가 값을 고치는 순간 원래 AI 추정값이 사라지는(덮어써지는) 구조였어서, "AI가 뭐라고 했고 트레이너가 뭐라고 고쳤는지"를 짝지어 볼 방법이 없었다 — 이번 작업은 정확히 이 손실을 막는 것이었다.

### 8-2. 이번에 만든 것
1. `FootManualToeInput`에 `estimatedBeforeValue`/`estimatedAfterValue`를 추가해 AI의 원본 시뮬레이션 값을 영구 보존.
2. 트레이너가 값을 고친 항목 옆에 "AI 추정 대비 얼마나 달랐는지"를 바로 보여주는 UI 힌트(`FootResultsPanel.tsx`의 `CorrectionHint`).
3. XMSK 데이터 품질 대시보드(로그인 후 XMSK 탭 → "데이터 품질")에 세 번째 섹션 "발가락 마디별 시뮬레이션"을 추가해, 항목별로 몇 건이 트레이너 확인을 거쳤는지·평균 보정폭이 얼마인지를 직접 확인할 수 있게 함.

자세한 코드 위치와 설계 근거는 `CLAUDE.md`의 "발가락 마디별 시뮬레이션 — 'AI 추정 vs 트레이너 실측' 보정 데이터 파이프라인" 절 참고.

### 8-3. 다음 판단 기준 — "언제 옵션 B를 실제로 시작하는가"
6장 표 5번("데이터 품질 대시보드")이 이제 발 기능에도 적용됐으므로, 앞으로는 이 화면의 "발가락 마디별 시뮬레이션" 섹션을 주기적으로 확인해 다음 기준이 충족되면 그때 옵션 B(경량 보정 모델) 실제 학습에 착수하는 것을 권장한다:

- 항목당(20개 중 특히 사용 빈도가 높은 엄지 MTP/IP부터) 트레이너 확인·보정 건수가 최소 50~100건.
- 평균 보정폭(`avgAbsCorrectionDeg`)이 우연한 오차 수준을 넘어 일관되게 크게(예: 참고 상한 `referenceMaxDeg`의 상당 비율) 나오는 항목 — 이런 항목이 결합계수(`coupling`) 재조정의 우선순위가 된다.

이 기준에 도달하기 전까지는 계속 6장의 1차 완성 로드맵(트레이너 실측 입력 UI 확장, 결과-버전 태깅, 데이터 품질 대시보드 — 이번 작업까지 포함해 사실상 대부분 완료)을 다른 기능(손·발 EEG 연동 등)에도 같은 패턴으로 넓혀가며 앱을 고도화하는 것이 맞다. "충분히 쌓였는지"를 감으로 판단하지 않고 이 대시보드 숫자로 판단하자는 것이 이번 작업의 핵심 취지다.

## 9. 진행 상황 업데이트 (2026-09-15) — 손가락 관절 14개에도 같은 패턴 확장 (단, ROM식으로)

8장 작업 직후 사용자가 "손가락마디별 시뮬레이션도 나오게 해달라"고 요청했다. 구현 전에 먼저 확인 질문을 던졌는데, 발가락과 손가락은 AI가 값을 내는 방식 자체가 다르기 때문이다 — 발가락은 개별 관절을 인식할 모델이 없어 "신호 하나를 결합계수로 배분하는 시뮬레이션"이 필요했지만, 손가락 14관절(`HandJointResult`)은 이미 MediaPipeHands 21랜드마크로 관절마다 직접 측정한 값이다. 사용자는 "트레이너 확인/보정 + 보정 데이터 수집" 방향을 선택했다 — 즉 8장과 같은 목적(옵션 B 착수 여부를 데이터로 판단)이지만, 발가락식 시뮬레이션으로 되돌리는 것이 아니라 ROM(`xmskEstimates`)이 이미 쓰던 "AI 계산 vs 트레이너 실측" 정답값 수집 패턴을 그대로 붙이는 방식이다.

### 9-1. 발가락 패턴과 무엇이 다른가
- 발가락(`FootManualToeInput`)은 "AI 시뮬레이션 초기값 → 트레이너가 덮어씀"이라는 **상태 전이**가 있고, 그래서 원본 시뮬레이션 값을 잃지 않게 보존하는 게 8장 작업의 핵심이었다.
- 손가락은 AI 계산값 자체가 이미 정확도를 검증할 대상이지, 트레이너가 "고쳐 쓸" 잠정값이 아니다. 그래서 별도 `HandJointGroundTruth{ id, verifiedValue }` 필드에 트레이너 실측값을 나란히 저장하기만 하면 된다(ROM의 `RomXmskGroundTruth`와 완전히 같은 방식). "평균 보정폭"(AI값 vs 트레이너 수정값의 차이) 같은 지표는 손가락엔 성립하지 않는다 — 대신 데이터 품질 대시보드에서는 항목별 수집 건수(`withEstimate`/`withGroundTruth`/수집률)만 보여준다.
- 이 데이터가 쌓이면 판단할 수 있는 것도 다르다: 발가락 데이터는 "결합계수(`TOE_SEGMENT_SIM_PARAMS`)를 다시 맞출 시점"을 알려주지만, 손가락 데이터는 "포즈 인식 파이프라인(MediaPipeHands 기반 각도 계산) 자체가 실제 관절 각도와 관절별로 얼마나 정확한지"를 알려준다 — 후자는 옵션 A(포즈 추정 모델 재학습)의 필요성을 판단하는 데도 쓰일 수 있는 데이터라는 점에서 8장의 발가락 데이터보다 조금 더 근본적인 신호다.

자세한 코드 위치와 설계 근거는 `CLAUDE.md`의 "손가락 관절 14개 — 'AI 계산 vs 트레이너 실측' 정답값 수집" 절 참고. 판단 기준(항목당 최소 수십 건, 데이터 품질 대시보드로 확인)은 8-3절과 동일하게 적용한다.
